# Lilly専用管理（旧データ移行前）

`01-lilly.sql` は隔離環境で先に検証する。新規保存機能を本番で有効にする前に、スタジオと予約サイトの取扱範囲を確認する。Lilly専用の呼び名列は設けず、共通の nickname を使用する。旧サービス行は読み取りで保持し、Lillyの専用登録から受講記録を生成しない。

## 旧Lilly所属の移行準備

`review-candidates.sql` の読取結果を本人限定で照合する。顧客IDと旧紐付けIDを用い、通常37人、顧客アーカイブ済み9人、手入力済み所属1人という調査時点の内訳を適用直前に再確認する。スタジオの取扱範囲と対象IDが承認されるまで追加しない。

将来の移行では、承認済みIDと元の旧紐付けを再照合し、既存のLilly所属行がある顧客はアーカイブ行を含め除外する。顧客×グループの一意制約と競合時追加なしで再実行を安全にする。専用プロフィールへの転記は別途承認し、元値を保持する。旧行、third_place、顧客アーカイブ、氏名、NUSの状態はそのまま維持する。

## 切り戻し

UIを戻す場合も専用データと旧行保護のSQLを保持する。名前なし顧客が存在すると旧UIでは氏名表示や編集が成立しないため、切り戻し中は対象顧客の編集を止める。氏名の必須制約へ戻す変更は名前なし顧客の扱いを別途決めてから行う。

## 公開順序と停止条件

1. スタジオの取扱範囲と公開の承認を確認し、現行版の復旧先と復元検証済みの復旧点を確保する。旧Lilly行・顧客・カルテ・third_place・権限を適用直前に読み取り照合する。
2. 既存行の移行なしでSQLを適用する。DB適用後は旧画面のLillyサービス行の編集・削除を停止する。旧画面が既存行の種別変更や削除を送信しても、新RPCは旧行を保持する。
3. 既存データ・認可を照合し、新規プロフィールが空であることを確認してからアプリを公開する。照合が外れたら公開を止める。
4. 本人の実機で検索・カルテ・呼び名表示を確認する。ロールバック時は専用項目の編集と、名前なし顧客の旧画面での編集を止める。

移行は通常顧客とアーカイブ済み顧客を別の対象一覧にする。各一覧で、所属を追加する対象、会員種別を正規化する対象、ヨガを引き継ぐ対象を個別に承認する。会員種別やヨガを承認した場合も、移行直前に旧行と手入力行を再照合し、競合があれば当該顧客を除外する。顧客アーカイブは解除しない。
