# CRM STEP 1 適用・復旧手順

本番適用前に対象プロジェクトと本人アカウントを照合し、利用者の指定と本番作業について明示承認を得る。本人のUUIDは運用者の承認済み入力として扱い、ソース、チケット、ログに記載しない。

## 適用順序

1. 検証環境で合成データを使い、SQLとアプリを検証する。アプリの接続先を検証用DBに固定する。本番適用直前には参照先、CRM全5表のRLS・実効権限、関数所有者と定義、既存4種類の件数・IDと紐付けを再確認し、安全な保管先に復旧用の情報を記録する。
2. 管理用DB接続で `01-prepare.sql` を適用する。既存RLSを使い、必要なCRUDだけを残す。有効な管理者状態をDBで確認し、原子的な登録RPCを追加する。旧画面の失敗時処理に必要な顧客DELETEはこの時点で維持する。
3. 管理者接続の同一トランザクションで、承認済みUUIDをバインドして `set_config('crm.approved_owner_id', …, true)` を呼び、`02-owner-only.sql` を実行する。本人が有効な管理者であることを検証してからコミットする。承認済みUUIDの値をSQLファイルに埋め込まない。本人・テスト用管理者の双方でRLSの判定を確認する。
4. 新しいアプリを公開し、本人の既存顧客の閲覧とCRM画面の認可を確認する。登録RPCの書き込みテストは合成データの検証環境で行う。旧クライアントが使われていないことを確認し、残っている場合はCRM画面の再読み込みを案内する。
5. `03-remove-customer-delete.sql` を適用し、利用者の顧客DELETE権限がなくなったことを確認する。既存顧客の件数・ID、担当先・サービス紐付け、カルテの件数を再照合する。

## 復旧

- SQL適用中の失敗はコミットせず取り消す。適用後に本人が拒否された場合は、管理用接続から、承認済み本人を示す単一行とプロフィールの状態を照合して復旧する。一般ユーザーやテスト用管理者へのCRM許可、過剰権限を復旧に使わない。
- アプリを切り戻す場合、原子的な登録RPCを使用する互換ビルドを選ぶ。物理削除に依存する旧ビルドしかない場合は登録を一時停止する。CRM利用者の制限と顧客DELETEの廃止を維持する。
- 既存レコードの差分が見つかった場合は関係する操作を停止し、適用前に記録した件数とIDを保護された環境で比較する。原因を調査し、復元が必要な場合は検証環境で復元対象を確認する。

## 隔離検証

`verify-local.sql` は既存スキーマの関連部分を模した合成データ用です。空のローカルDBだけで実行します。コンテナ内の `/crm-test` にこのディレクトリを読み取り専用でマウントし、外部ネットワーク無効で `verify-local.sh` を実行できます。SQL検証と別に、検証環境でSupabase Auth、Data API、画面、既存一般機能を通した受入確認を行います。

### Auth、Data API、ブラウザの受入検証

リポジトリのルートで、検証専用のComposeプロジェクトと一時DBを起動する。既存の環境ファイルは変更しない。Auth、Data API、テスト用ゲートウェイ、Next.jsはいずれもループバックで使用する。実際のAuthトークンは合成アカウントから取得し、出力に含めない。検証専用Chromeプロファイルを使い、Chromeからの `supabase.co` への通信をブロックする。

```text
docker compose -p crm-step1-acceptance -f supabase/rollouts/crm-step-1/acceptance.compose.yml up -d --pull never
node supabase/rollouts/crm-step-1/acceptance.cjs --seed --browser
docker compose -p crm-step1-acceptance -f supabase/rollouts/crm-step-1/acceptance.compose.yml down
```

`--seed` は空の検証環境で一度だけ指定する。Chrome付きの実行はWindowsの標準インストール先を使う。既存一般機能は、合成データの辞典・シークエンス・プリセット表示、プロフィール編集、退会申請と取り消しを確認する。シークエンス編集やプリセットの取り込みなど、CRM認可と独立した操作はこの検証の対象外。
