# CRM 所属階層・段階A

段階AはM.glitter、NUS、Lillyの所属と統合フォームを追加する。既存顧客・事業の一括移行は含まない。明示したM.glitterブランドは、既存事業行を参照する新しい所属行として保持する。チェックを外した所属はアーカイブし、従来の事業メモ・区分・カルテを保持する。NUSの所属変更は既存のNUS事業関係のアーカイブ状態に反映する。旧NUS登録経路も明示操作の際は所属と同期する。

既存の「担当先×サービス」の入力・表示は維持する。Lillyの新規サービス紐付けからM.glitterの事業を自動追加しない。過去のLilly由来の事業行はそのまま保持する。Lillyの契約・受講入力、新しいNUS区分、最上位グループによる一覧フィルターは後続段階で確認・対応する。

## 検証

- ネットワーク無効の一時PostgreSQLに `supabase/rollouts` を `/crm-test` として読み取り専用マウントし、Bashで `/crm-test/crm-membership-a/verify-local.sh` を実行する。
- Auth、Data API、ブラウザはSTEP 1のローカルComposeを空の状態で起動し、`node supabase/rollouts/crm-step-1/acceptance.cjs --seed --membership-a --browser` で確認する。実行後に検証専用Composeを終了する。

## 適用と復旧

本番適用には別途承認が必要。適用直前に本番のCRM本人認可、Lilly担当先ID 1、復元可能なバックアップ、既存顧客・サービス紐付け・カルテ・事業・NUS情報の照合値を確認する。`01-memberships.sql` を先に適用し、追加表が空で既存データが保持されていることと新規権限を確認してから画面を切り替える。

画面切り戻しでは追加された所属データとNUSの履歴を保持する。旧画面では新しいグループ・ブランド所属の確認と編集ができない。旧版の登録動作を利用する場合も、Lillyからの誤分類を避けるトリガーを維持する。
