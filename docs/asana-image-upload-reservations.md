# 非公開画像アップロード 工程Aのレビュー

対象は予約台帳と容量・頻度の判定。現行API、編集画面、画像参照、Storageポリシー、回収ジョブには接続しない。

## 追加する定義

| 定義 | 用途・権限 |
| --- | --- |
| `asana_image_private.settings` | 設定とトランザクションロック用の1行。DB管理者がレビュー済みSQLで変更する |
| `asana_image_private.reservations` | 予約ID、所有者、パス、状態、予約・確定容量、時刻。パスと予約IDは一意 |
| `asana_image_private.attempts` | 予約を取得した試行だけを記録。所有者・時刻に索引 |
| `asana_image_private.usage_totals(uuid)` | Storageの実サイズ、予約、異常件数を照合する内部関数 |
| `public.asana_image_reserve(uuid,uuid)` | サーバーがAuthで確認したIDと予約IDで予約。実行権限は `service_role` のみ |
| `public.asana_image_settle(uuid,uuid,text,text)` | 所有者・予約ID・パスが一致する状態変更。実行権限は `service_role` のみ |

内部表はRLSを有効化し、直接アクセスを許すポリシーは作らない。新設関数の `search_path` は空に固定する。容量・頻度は複数インスタンスで共有され、各操作が先に同じ設定行をロックする。ロック中にネットワーク呼び出しは行わない。

## 予約と整合性

- `held` は保存処理の開始前。開始期限は10分。期限切れの `held` は開始できない。保存されていなければ信頼できるサーバーから `release` できる。期限だけでは自動で解放しない。
- `start` の初回成功で `writing` になる。再送された `start` は拒否し、2回目のStorage書き込みを始める理由にしない。再送された予約は同一行を返して履歴を増やさない。
- `confirm` はStorageのメタデータを直接読み、確認済みWebPの実サイズを記録する。クライアント申告サイズは受け取らない。状態が `confirmed` になれば容量計算では実オブジェクトのみを数える。
- `writing` の解放に使う `failed` は、サーバーがStorageから書き込みなしと確定できた拒否を受け取った場合に限る。応答が不明なら `uncertain` として全量を保持する。確認できた実ファイルは確定可能。ファイルがない未確定分の決着には、後工程で別途照合・復旧手順が必要。
- 存在するファイルは参照の有無を問わず集計する。処理中は実ファイルが既にあっても予約を加えるため、一時的に多めに見積もる。サイズ不明または確定台帳と実ファイルの欠落・差がある場合は新規受付を止める。集計値はStorageの実データから導出するため加減算の二重実行がない。
- 一般予約には移行用70 MiBを使わせない。全バケットの現在容量を含めて判定する。旧公開バケットや別の管理経路による書き込みは同じロックを取らず、組織の別プロジェクトもSQLの集計対象外。700 MiBは新API経由の受付境界。
- ローカルで採用する試行履歴保持方針は7日。後工程で小バッチの削除を別途承認する。頻度は直近24時間の履歴だけを使う。拒否リクエストは履歴に追加しない。予約IDの再利用防止のため、終端した予約行は履歴整理と一緒に削除しない。

## 本番適用前と切り戻し

1. 名前の衝突がないこと、`profiles.plan` が本人入力で書き換えられないこと、対象列とStorageのサイズ・MIMEメタデータが想定どおりであることを読み取りで確認する。組織全体の枠と既存データ・権限の件数と照合値を取得する。
2. フラグ無効のままSQLを適用し、予約0件、既存RLS・権限・データの照合値が一致することを確認する。工程Bで、サーバーが検証したIDだけを渡し、`start` 初回成功後に上書きなしでStorageへ書く。予約の戻り値 `request_bytes` に従い、Content-Type・実WebP・サイズも検証する。既存の直接削除と参照登録を手当てするまでは有効化しない。
3. 工程Aのみで台帳が未使用なら、公開RPC2件、内部関数、子から順に試行表・予約表・設定表、空の専用スキーマを同一トランザクションで撤去できる。未確定・確定ファイルが存在する場合は処理を止め、台帳を保持して照合する。切り戻しSQLで実ファイルや既存参照を削除しない。

隔離テストは専用の空コンテナを使う。

```powershell
docker compose -p asana-reservation-acceptance -f supabase/rollouts/crm-step-1/acceptance.compose.yml up -d --wait db
node --test tests/asana-image-reservations.test.cjs
docker compose -p asana-reservation-acceptance -f supabase/rollouts/crm-step-1/acceptance.compose.yml down
```
## 工程Bの保存と参照解除

`05-upload-image-references.sql` を工程Aの後、アプリ公開前に適用する。非公開アップロードはフラグを有効にするまで停止したままとする。工程BのSQLは非公開バケットの所有者向け直接削除ポリシーを撤去し、読み取り・署名制限と旧公開バケットには触れない。現行UIはファイルの直接削除を呼ばない。

画像参照の変更は既存のアーサナRLSと参照検査を通る。画像を変更する編集は、読み込んだ公開URL・非公開パスが両方一致する場合だけ保存する。差し替えと参照解除では公開URLもクリアし、既存ファイルは保持する。

回収候補は、予約台帳の `confirmed` で、辞書に参照がなく、`coalesce(unreferenced_since, updated_at)` から24時間を経過したもの。確認済みのまま一度も参照されなかった画像は確定時刻、以前参照された画像は最終参照解除時刻を使う。移行画像など予約台帳に存在しないパスは、この候補に含めない。

工程Cでは、共有の設定行をロックして参照・所有者・Storageの状態を再確認し、新しい参照を拒否できる状態に確定してからStorage APIで削除する。DB行のロックを外す前に、別トランザクションからもその状態を確認できる必要がある。削除完了後は工程Aの集計と矛盾しないよう台帳を整合させる。結果不明時は予約を保持し、期限切れだけを根拠に容量を解放しない。試行履歴の整理は7日間の保持と予約への外部キーを考慮する。

アプリの切り戻し先は非公開画像を読める互換版。先にアップロードを停止し、参照列・画像・台帳は保持する。工程BのDB定義を戻す必要がある場合は、新規アップロードと画像編集を停止し、台帳・参照の状態を照合した上で個別に判断する。直接削除ポリシーの再作成は、台帳とStorageの整合が崩れる可能性があるため、通常のアプリ切り戻しには含めない。

## 工程Cの手動運用

工程A、Bの順で適用済みの環境に `06-image-maintenance.sql` を適用する。工程Cは予約台帳に回収開始時刻を追加し、工程Bと同じロックで参照の再登録を拒否する。管理RPCは `service_role` 限定で、新しい画面や定期処理は不要。

既存の管理資格情報をローカルの一時環境変数 `ASANA_MAINTENANCE_SERVICE_KEY` に設定し、対象のURLを `ASANA_MAINTENANCE_URL` に指定する。キーは非表示入力で扱い、処理後に環境変数を除去する。操作は1人が1プロセスずつ行い、途中で異常終了したときは前のプロセスが停止済みであることを確認する。以下は適用承認後の手順で、本番の書き込みには `--production` が必要。

| コマンド引数 | 内容 |
| --- | --- |
| `inspect` | dry-run。候補件数、合計バイト数、復旧可能・要調査件数、整理可能な履歴件数を出力 |
| `reclaim` | 最大10件。回収を確定して再参照を止め、Storage APIで削除。再照会で不存在を確認し、DBでも参照・メタデータの不存在を確認して台帳を解放 |
| `recover` | 最大10件。期限切れの `held` は開始不能・オブジェクトなしの場合に解放。`writing`・`uncertain` は取得したファイルのサイズとStorageメタデータを照合し確定 |
| `prune` | 7日より古い試行履歴だけを整理。予約台帳や添付画像は保持 |

例は `node supabase/rollouts/asana-image-privacy/maintain-images.mjs inspect`。回収・復旧・整理の前後に `inspect` を実行する。出力は件数・容量・状態だけで、キー、画像パス、所有者IDを含まない。

ファイル不存在の根拠がない削除失敗は、回収マーカーを保持して停止する。再実行は回収途中の候補を優先し、削除済みと確認できたものは再削除せずに確定する。Storage削除から台帳確定までに中断すると、工程Aは容量の照合を要求して新規予約を一時停止する。削除先を確認できない `writing`・`uncertain` は、期限にかかわらず保持し、個別調査に回す。回収対象は台帳のある本人パスだけ。旧公開、所有者不明、台帳のない移行画像は対象外。

隔離試験は新しい試験コンテナに上記の受入コマンドから `--image-browser-only --browser` を外して合成データを用意し、`node --test tests/asana-image-maintenance.test.mjs` を実行する。ローカルのPostgreSQL、PostgREST、Storageのみを使用する。

### 適用・切り戻し

工程B SQL → 工程C SQL → フラグ無効の互換アプリで確認、の順。Bの非公開バケット直接削除ポリシー撤去に伴い、アプリでは画像の参照解除を使用し、運用者はCの手動回収を使用する。B以前の対応済みアプリは非公開画像を閲覧できる。アップロードを有効にする前に、DB権限・署名制限・非公開バケット設定、既存のサーバー資格情報の管理、互換版への切り戻し、本人の確認計画を照合する。

障害時は先にアップロードと手動処理を止め、互換版へ切り戻す。工程Cを一度も回収に使用していない場合は `06-rollback-unused-image-maintenance.sql` を使用できる。回収開始履歴がある場合はSQLが停止するため、処理の状態を照合して復旧する。工程Bの定義は、工程Cが依存している間は撤去しない。BのDBを戻す必要がある場合は、画像参照と台帳が未使用であることを確認し、Cを戻した後、Bの参照追跡トリガー・関数・列を取り消してから、元の削除ポリシーを復元する。

### B・Cを個別トランザクションで適用する手順

1. 双方のSQL原本と切り戻しSQLのハッシュを確認する。フラグ無効、非公開画像・パス・予約・試行履歴が各0件、工程Aの設定と権限、既存データの照合値、`postgres` に対する `storage.objects` のポリシー管理委任を確認する。
2. Bの原本を `postgres` ロールで実行する。Bのコミット後、参照追跡の列・関数・トリガー、直接削除ポリシーの撤去、読み取り・署名制限の維持を読み取りで確認してからCの原本を実行する。両原本は個別にトランザクションを持つ。
3. Cのコミット後、管理RPCと再参照ガード、固定 `search_path`、権限、工程Aの設定、各0件と既存照合値を再確認する。本番で管理RPCを試験実行しない。
4. 応答断では再実行前に別の読み取り接続で両工程の適用状態を確認する。Cが未適用でBだけが残った場合、未使用条件を満たせば `05-rollback-unused-image-references.sql` で戻す。Cまで適用されている場合は、未使用条件を確認してC→Bの順に戻す。回収開始履歴、予約・試行履歴、非公開画像または参照があれば、切り戻しSQLで消さず個別に照合する。
